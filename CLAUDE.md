## What this is
One platform made of three apps, built from a blank canvas:
- **Speak**: Dictate, Speech and Meeting modes in one app. **Meeting mode is built. Dictate mode is built (first version, 2026-10-11). Speech mode is built (first version, 2026-10-13; list views and Draft per the owner's spec the same day); owner's first real-Azure run worked.**

- **Widget**: system-wide dictation overlay. **First version built 2026-10-13 as a browser extension (Edge/Chrome); owner's first real use worked, 2026-10-14.** See the Widget section and `docs/widget.md`. **Widget for Windows** (any Windows program) built 2026-10-23; owner confirmed it in desktop Outlook and WhatsApp the same day; see `docs/widget-windows.md`.

Repo: `ashleylipke-sketch/VerbaFlow` (GitHub). Decisions already made by the owner: build the foundation and Speak Meeting mode first, code lives in this repo, **stand-ins now, Azure later** (every Azure service sits behind an interface in `VerbaFlow.Core/Providers`).

## Stack and layout
.NET 10 (Core, Infrastructure, Api, Tests), minimal API, SQLite standing in for Azure SQL (JSON document tables plus a hash-chained append-only audit table), React 19 + Vite 7 + TypeScript in `web/` (built into `src/VerbaFlow.Api/wwwroot`, git-ignored), vitest, Playwright for browser checks.
- `src/VerbaFlow.Core`: domain, permissions, audit chain, transcripts, provider interfaces. No dependencies.
- `src/VerbaFlow.Infrastructure`: SQLite, media store, services, Azure adapters (`Azure/`), stand-ins (`StandIns/`), `Services/FfmpegAudioEnhancer.cs`.
- `src/VerbaFlow.Api`: endpoints, dev auth, background worker.
- `docs/`: decision record, data model, and one setup guide per Azure service.

## Rules that must not be broken (all enforced and tested)
- Approval locks the item; the database enforces it with triggers (JSON key is camelCase `$.status`).
- Reopen needs two different admins.
- Audit chain is SHA-256, append-only. Media is write-once.
- Permission order: lock, then role, then admin and grants.
- Speaker renames are NOT tracked as transcript changes. Edits are tracked word by word against machine version 1 (original struck through until approved).
- Original recordings are never altered. Only a processing copy is cleaned up.

## Deleting recordings (built 2026-10-10, owner's rules)
- Never approved: the author/importer or an admin deletes at once with a reason (`POST /items/{id}/delete`, action `delete`).
- Approved: must be reopened first (existing two-admin reopen). Deleting the reopened version needs a `DeleteRequest` (`POST /items/{id}/delete-request`, action `request-delete`) agreed by two different admins; an admin who asks counts as the first (owner's words: "two admins need to approve"). Admins see it on the Reopen and delete requests page.
- A delete removes every version in the chain: audio files, transcripts, summaries. Items stay as tombstones (`Status = Purged`, label "Deleted", `DeletedAt/By/DeleteReason`), media records (hash) stay, audit trail stays (`item.deleted`, `delete.requested/approved/rejected`). The DB trigger lets a Completed item change only to Purged; Purged never changes. Speaker names given in renames remain in the audit trail.
- **Owner's first try (2026-10-10, unapproved item, Windows, repo inside OneDrive) failed half way**: audio files were removed but the item was not marked deleted, so the player then hit FileNotFound. Cause not seen (likely a file or folder held by the open player or OneDrive). Fixed: stored files are opened with FileShare.Delete, `DeleteContentAsync` retries and never throws (returns removed/failed; audit `audioFilesNotRemoved`), the empty-folder removal is best effort, and a missing file gives "The recording is missing." (404) instead of a crash. Running Delete again finishes a half-done deletion. **Owner confirmed the fixed delete of an unapproved item works (2026-10-10).** **Owner confirmed the reopen then two-admin delete of an approved item works (2026-10-11).**

As in Word, making any other change after an Undo leaves nothing to redo. `VersionKind.Redo` (also uses `UndoneTo`), `Transcript.RedoStep`/`Redo` (works out the undone steps from the run of Undo/Redo versions at the end), `POST /items/{id}/redo`, `TranscriptView.Redo`, audit `transcript.redone` (forwardTo, redid); a redone rename goes back into the summary too. Restore in the Versions card still brings any version back. Audit `transcript.undone` (version, backTo, undid, changedInSummaryAndMinutes).
